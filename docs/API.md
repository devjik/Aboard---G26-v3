# Aboard — API Reference

All custom endpoints live under `/api/v1` and return a consistent JSON envelope:

```ts
// Success
{ "ok": true, "data": T, "meta": { "correlationId": "corr_..." } }

// Error
{ "ok": false, "error": { "code": "VALIDATION", "message": "..." }, "meta": {...} }
```

Every request includes an `x-correlation-id` header (auto-generated by the
client). Errors use the codes defined in `src/lib/api/envelope.ts`:
`BAD_REQUEST`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION`,
`CONFLICT`, `SEAT_UNAVAILABLE`, `LOCK_EXPIRED`, `RATE_LIMITED`,
`IDEMPOTENCY`, `INTERNAL`.

## Auth

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/v1/auth/register` | `{ name, phone, email?, password, role, institution?, studentIdNumber? }` | `{ user: AuthUser }` |
| POST | `/v1/auth/login` | `{ phone, password }` | `{ user: AuthUser }` |
| POST | `/v1/auth/otp/request` | `{ phone }` | `{ otpSent, devCode? }` |
| POST | `/v1/auth/otp/verify` | `{ phone, code }` | `{ user: AuthUser }` |
| POST | `/v1/auth/email-otp/request` | `{ email }` | `{ otpSent, channel, devCode? }` |
| POST | `/v1/auth/email-otp/verify` | `{ email, code }` | `{ user: AuthUser }` |
| POST | `/v1/auth/refresh` | — | refreshes access token via httpOnly cookie |
| POST | `/v1/auth/logout` | — | `{ ok }` |
| GET | `/v1/auth/me` | — | `{ user: AuthUser }` |

## Trips & seats

| Method | Path | Query/Body | Returns |
|---|---|---|---|
| GET | `/v1/trips/search` | `?from&to&date&maxPrice&timeWindow&minRating&minSeats&page&pageSize` | `{ items: TripSummary[], total }` |
| GET | `/v1/trips/:id` | — | `TripDetail` |
| GET | `/v1/trips/:id/seats` | — | `{ tripId, basePricePesewa, seats: SeatInfo[] }` |
| POST | `/v1/trips/hold` | `{ tripId, seatLabel }` | `{ lockId, seatLabel, expiresAt, pricePesewa }` |
| POST | `/v1/trips/hold/:lockId/release` | — | `{ ok }` |

**Seat hold semantics:** the hold is atomic via a Prisma transaction +
`@@unique([seatId, tripId])` constraint on `SeatLock`. Two simultaneous
holds on the same seat return `SEAT_UNAVAILABLE (409)` for the loser.
Holds expire after 5 minutes (`SEAT_HOLD_TTL_MS`).

## Bookings & payments

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/v1/payments/initiate` | `{ bookingIntentId, tripId, seatLabel, amountPesewa, payerRole, idempotencyKey }` | `{ paymentId, providerRef, status, devConfirmToken? }` |
| POST | `/v1/payments/:id/confirm` | — | `{ ok, paymentStatus, bookingStatus, ticketId, ticketToken, ref, route, seat, departureAt, studentName }` |
| GET | `/v1/tickets/:bookingId` | — | `{ ticketId, status, version, issuedAt, token, qr, ref, payload, route, seatLabel, studentName, departureAt, departureFormatted, operatorName, paymentStatus, approved }` |
| POST | `/v1/tickets/scan` | `{ token, driverId, lat?, lng? }` | `{ ok, ticketId, status, conflict? }` |

**Idempotency:** `POST /v1/payments/initiate` requires an `idempotencyKey`.
Duplicate keys return the original payment record instead of creating a new one.

**Webhook (future):** `POST /v1/payments/webhook` — receives provider
webhook, verifies HMAC signature, dedupes via `webhook_events` table,
updates payment + booking, triggers ticket issue. Currently stubbed
because the sandbox provider uses `/confirm` directly.

## Driver trip lifecycle

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/v1/notifications/trip-started` | `{ tripId }` | `{ ok, studentsNotified, parentsNotified, adminsNotified }` |
| POST | `/v1/notifications/boarding` | `{ tripId, studentId, distanceMeters, driverLat, driverLng, studentLat, studentLng }` | `{ ok, parentsNotified }` |
| POST | `/v1/notifications/meetup` | same as boarding | `{ ok, studentsNotified, parentsNotified, adminsNotified }` |

Driver position broadcast goes over Socket.IO (port 3003) to the trip's
room, not over REST. The client hook `useTrackingSocket` manages the
connection.

## Rate limiting

Not yet implemented in the local build. For production, add rate limiting
on `/v1/auth/*`, `/v1/trips/search`, and `/v1/payments/*` via Vercel Edge
Middleware or Upstash Redis rate limiter. See `docs/PHASE2.md`.

## OpenAPI

A full OpenAPI 3.1 spec is deferred to phase 2. The contract types live in
`src/lib/api/contracts/*.ts` as Zod schemas, which can be compiled to
JSON Schema and wrapped in an OpenAPI document via `zod-to-openapi` when
needed.
